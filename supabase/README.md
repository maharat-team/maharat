# Maharat backend setup

Do these in order. Replace `yourdomain.com` with your domain.

## 1. Apply the migrations

Stop if your project already has tables with these names: the migrations use plain `create table` and will fail rather than change anything.

**Option A: CLI** (asks for your database password)

```sh
npx supabase login
npx supabase link --project-ref <your-project-ref>
npx supabase db push
```

**Option B: SQL Editor.** Paste each file from `migrations/` and run them in filename order.

## 2. Verify your domain in Resend

Resend > **Domains** > **Add Domain**. A subdomain such as `mail.yourdomain.com` keeps auth email reputation separate from your main domain. Resend generates the DKIM key, so copy the exact values from the domain's **Records** tab.

| Purpose | Type | Name | Value | Priority |
|---|---|---|---|---|
| DKIM | TXT | `resend._domainkey` | Generated by Resend | |
| Return path | MX and TXT, or CNAME | `send` | Generated by Resend | As shown |
| DMARC (recommended) | TXT | `_dmarc` | `v=DMARC1; p=none; rua=mailto:dmarc@yourdomain.com;` | |

The record types and values on the Records tab are the source of truth, and the domain must show **Verified** there before sending.

If your DNS provider proxies records (Cloudflare), set them to **DNS only**. Move DMARC to `p=quarantine` once mail is passing.

Then create an API key: Resend > **API Keys** > **Create**, with **Sending access** for this domain.

## 3. Custom SMTP in Supabase

Authentication > **Emails** > **SMTP Settings** > enable custom SMTP. Do this before editing the templates.

| Field | Value |
|---|---|
| Sender email | `no-reply@yourdomain.com` (must be on the verified domain) |
| Sender name | `Maharat` |
| Host | `smtp.resend.com` |
| Port | `465` |
| Username | `resend` |
| Password | Your Resend API key (`re_...`) |

The Resend key stays in the Supabase dashboard. Do not add it to this repository or the app.

## 4. Email templates and OTP settings

1. Authentication > **Emails** > **Templates**: paste `email_templates/otp_code.html` into **both** **Magic Link** and **Confirm signup**. New users receive Confirm signup, so changing only Magic Link sends first-time users a link instead of a code.
2. Authentication > **Sign In / Providers** > **Email**:
   - Enable the Email provider and keep **Confirm email** on.
   - **Email OTP Expiration**: `600` seconds, which matches the template text.
   - **Email OTP Length**: `6`.
3. Authentication > **Rate Limits**: the default email limit is low. Raise it to suit expected sign-ups.

## 5. Approving workers

There is no admin panel yet. New workers stay hidden until approved. Open their photos under Storage > `cnic-documents` > their user id, then run this in the SQL Editor:

```sql
-- Who is waiting
select v.worker_id, w.full_name, w.trade, v.cnic_number, v.submitted_at
from public.cnic_verifications v
join public.workers w on w.id = v.worker_id
where v.status = 'pending'
order by v.submitted_at;

-- Approve
update public.cnic_verifications set status = 'approved'
where worker_id = '<worker-id>';

-- Reject, with the reason the worker will see
update public.cnic_verifications
set status = 'rejected', rejection_reason = 'The CNIC photo is blurry.'
where worker_id = '<worker-id>';
```

## Security model

- The app ships only the project URL and publishable key. `SUPABASE_SECRET_KEY` bypasses RLS and is never used by the app.
- All tables have RLS. `anon` has no access; sign-in is required.
- Column grants stop users writing ratings, job counts or verification status.
- `cnic-documents` is upload-only for clients. Only the dashboard can view or delete those files.
